NexCode 项目架构导览

一个以 Textual TUI 为主界面的 Python AI 编程 Agent。核心不是单轮问答，而是“LLM 流式推理 → 工具执行 → 结果回填 → 继续决策”的自治循环，并在其上叠加上下文治理、记忆、多 Agent、权限和 MCP 扩展。

pyproject v0.2.0 Python ≥ 3.11 136 个 Python 模块 当前目录非 Git 仓库
01 · Project Positioning

先用一句话建立心智模型

NexCode 是一个“本地优先、文件系统持久化、可扩展工具注册表驱动”的编码 Agent Runtime。Textual、CLI 和 WebSocket 只是入口；真正的产品核心位于 NexCode/agent.py 的事件循环。

它解决什么问题

  • 在终端中完成代码检索、编辑、命令执行与多轮自主决策。
  • 把不同模型提供商统一为同一套流式事件和工具调用协议。
  • 在长会话里控制工具输出体积，并自动压缩上下文、恢复关键工作状态。
  • 通过 Skill、Markdown Agent、Hook、MCP 和自定义命令扩展能力。
  • 通过子 Agent、Team、共享任务、邮箱和 Git Worktree 支持并行协作。

主要架构风格

事件驱动 Agent Loop + Adapter（模型协议）+ Registry（工具/命令）+ 文件系统状态存储 + 分层安全检查。项目没有数据库，也没有重量级依赖注入容器。

最重要的阅读判断： app.py 很大，但它主要负责装配和 UI。理解项目时不要从 UI 细节陷进去，先读 agent.py。
当前成熟度： 主干测试覆盖较好，但 TUI、非交互子 Agent、远程模式存在重复装配和行为差异，已经出现 Hook、并发与能力集漂移。

04 · Agent Lifecycle

一次用户请求如何变成多轮自主执行

下面对应 Agent.run() 的真实顺序。Agent 不把工具当成外部附属能力，而是把工具调用和结果作为对话消息的一部分，持续送回模型。

STEP 1
注入运行上下文
Environment、NexCode/AGENTS 指令、长期记忆、Team 邮箱、后台任务通知。
STEP 2
执行前置 Hook
turn_start、pre_send，Prompt Hook 的输出拼入系统提示。
STEP 3
治理上下文
超大 ToolResult 落盘；接近窗口上限时摘要早期前缀并保留近期原文。
STEP 4
组装 LLM 请求
系统提示 + Provider 无关消息 + 已启用工具 schema，按协议序列化。
STEP 5
消费流式事件
Text、Thinking、ToolCall 增量被收集为统一 LLMResponse。
STEP 6
提前执行工具
完整 ToolCall 一到就创建 asyncio task；需要人工确认的调用延迟到流结束后。
STEP 7
结果回填
Assistant ToolUse 与 User ToolResult 成对写入 Conversation，更新真实 token 锚点。
STEP 8
继续或结束
有工具则进入下一轮；无工具则落盘 session、触发记忆提取/整理并发出 LoopComplete。

关键事件类型

事件用途
StreamText / ThinkingText驱动实时 UI 或结构化输出
ToolUseEvent / ToolResultEvent展示工具调用与执行结果
PermissionRequest通过 Future 暂停单个需要确认的工具
CompactNotification通知上层持久化 compact boundary
TurnComplete / LoopComplete区分工具轮次结束与整个请求结束
RetryEvent / ErrorEventmax_tokens 恢复、熔断或错误展示

Context Window 的两层治理

Layer 1：ToolResult Budget
单条超过 50,000 字符或同一批聚合超过 200,000 字符时，完整内容写入 .nexcode/session/tool-results/，对话只保留 2KB 预览和路径。
Layer 2：Auto Compact
有效窗口预留 20K 输出空间；软阈值再留 13K，硬阈值留 3K。摘要早期前缀，保留近期约 10K tokens / 至少 5 条消息，并避免拆散 tool_use 与 tool_result。

压缩后会重新附加最近读取的 5 个文件、已激活 Skill、当前工具目录和原始 transcript 路径，降低“摘要后失忆”。

06 · State & Persistence

状态模型：运行时内存 + 本地文件，没有数据库

Conversation、Task、Trace 在进程内；长期状态通过 JSONL、Markdown、JSON 和备份文件落盘。Team 数据默认位于用户目录，而不是项目目录。

.nexcode/config.yaml

Provider、权限模式、MCP、Hooks、Worktree、Team、Sandbox。

加载优先级：用户全局 → 项目 → 项目 local

.nexcode/sessions/

每个会话一份 JSONL + meta。恢复时从最后一个 compact boundary 开始重放。

审计保留压缩前原始记录

.nexcode/memory/

项目级 project/reference 记忆；用户级 user/feedback 位于 ~/.nexcode/memory/。

MEMORY.md 只做索引

.nexcode/session/tool-results/

超大工具输出的完整正文，Conversation 中只留预览。

避免上下文被日志或文件内容撑爆

.nexcode/file-history/

每个 session 独立目录

.nexcode/worktrees/

Provider 配置解析

项目策略
API Key显式配置优先，否则读取 ANTHROPIC_API_KEY / OPENAI_API_KEY

权限决策顺序

  1. Plan 模式例外工具/计划文件。
  2. 安全只读命令自动放行；危险命令硬拒绝。
  3. OS 沙箱开启时，命令通过规则检查后可自动放行。
  4. 文件路径必须位于项目或临时目录，并避开禁写配置。
  5. 用户/项目/local 规则匹配。
  6. 会话级 Allow Always。
  7. 权限模式矩阵兜底；仍为 ask 时触发 HITL。

OS 级沙箱只实现 macOS Seatbelt 和 Linux bubblewrap；Windows 当前返回 None。

07 · Extension Points

扩展能力不是一套机制，而是五条不同通道

它们分别解决“提示流程复用、Agent 角色、外部工具接入、生命周期策略、快捷命令”问题。使用前先选对扩展层。

Skill

Markdown/SKILL.md 或 skill.yaml + prompt.md，本质是可加载 SOP。支持 inline 与 fork。

目录：项目 .nexcode/skills 优先于用户目录

Sub-Agent Definition

带 frontmatter 的 Markdown，声明角色提示、工具白名单/黑名单、模型、轮次、后台和 worktree 隔离。

内置 Explore / Plan / General Purpose / Verification

MCP

连接 stdio 或 streamable HTTP Server，将服务端 schema 动态包装成 Tool。

默认 deferred，通过 ToolSearch 按需加载 schema

Hook

绑定 session、turn、tool、message、system 生命周期，执行 command/prompt/http/agent action。

pre_tool_use 可 reject；agent action 目前是 stub

Slash Command

本地命令或 Markdown prompt 命令，支持别名、参数提示和目录命名空间。

用户全局与项目级命令可合并

Native Tool

继承 Tool，提供 Pydantic 参数模型、category、并发安全与执行函数。

08 · Verification & Boundaries

测试证明了什么，以及当前最值得注意的技术债

结果来自当前 Windows 工作区按测试文件拆分执行。拆分运行是必要的，因为一个 consolidation 锁测试在 Windows 上会终止自身 pytest 进程。

566通过
2失败
1测试内跳过
2主动排除：Windows 锁检测 / 真实 LLM E2E
High · 已由测试暴露

交互主循环绕过 Tool Hook

Agent.run() 的流式直执行走 _execute_single_tool_direct，没有调用 pre_tool_use/post_tool_use。因此 reject Hook 未阻止 Bash，相关集成测试失败。

High · 并发语义漂移

非确认工具全部并发启动

流式路径把所有不需要 ask 的 ToolCall 都提交为 asyncio task，没有使用 partition_tool_calls 或 is_concurrency_safe。多个 Write/Edit/Bash 可能并发执行。

High · 运行时可能失效

Memory Consolidator 使用旧 API

consolidation.py 引用不存在的 BashTool/ReadFileTool 等名称，并使用过期的 Agent/PermissionChecker 构造参数。门控触发后大概率失败并回滚锁。

Medium · 架构重复

两个 Agent Loop 行为不一致

run() 与 run_to_completion() 重复实现循环，Hook、权限、并发、thinking、max_tokens 恢复和 memory 行为不同，子 Agent 与主 Agent 容易产生语义差异。

Medium · Composition Drift

三条入口分别装配依赖

TUI、CLI -p、Remote 都手工创建 Registry/Agent/Memory/MCP 等，Remote 已明显少于 TUI，新增能力容易只接入一条入口。

Medium · 命名不一致

MCP Tool 前缀有两套约定

Wrapper 生成 mcp_{server}_{tool}，而工具过滤、命令和 instructions 查找使用 mcp__{server}__{tool}，会影响 MCP 特权过滤与展示。

Medium · Skill Fork

Fork Skill 读取了错误字段

SkillExecutor 查找 agent._conversation，Agent 实际保存的是 _current_conversation，所以 recent/full 上下文很可能为空。

Low · Windows Portability

锁存活检测不安全

os.kill(pid, 0) 在 Windows 下不是可靠的存在性探测；对应测试会结束自身进程。Hook timeout 测试也硬编码 Unix sleep。

Low · 版本与文档

版本展示和文档落后

pyproject.toml 是 0.2.0，TUI banner 显示 0.1.0；根目录没有 README，NexCode.md 只有最小代码规范。

测试失败的区分： Hook timeout 失败属于 Windows 测试可移植性问题；pre_tool_use reject 失败是实际运行路径缺陷。当前页面没有修改这些源码，只做架构审阅和记录。

开始改代码前的三个提醒

  1. 先决定改的是核心 Agent 语义，还是某个 Surface 的展示/装配。
  2. 涉及工具执行时，同时检查交互 run 与非交互 run_to_completion。
